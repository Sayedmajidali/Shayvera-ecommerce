# Security Review

Review date: 2026-11-05 · Scope: entire application at the end of Phase 10 (local development build).

> Implementing these controls does **not** make the application "completely secure". This document records
> what was reviewed, what was changed, and the risks that remain. Re-review before production launch and
> after any significant change. A professional penetration test is recommended before handling real payments.

## 2. Issues found during the review and fixed

| #   | Severity | Finding                                                                                                                                                                                         | Fix                                                                                                 |
| --- | -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| 1   | High     | Admin pages relied on the layout guard only. In the App Router a shared layout is not re-rendered on client-side navigation, so a revoked/demoted session could still render other admin pages. | Every admin `page.tsx` now calls `requireAdminPage()` itself; APIs already enforced `requireAdmin`. |
| 2   | Medium   | Password complexity was only enforced in the browser.                                                                                                                                           | Better Auth `before` hook rejects weak passwords on sign-up, reset and change.                      |
| 3   | Medium   | Rate-limit key used the left-most `X-Forwarded-For` value, which clients control.                                                                                                               | `clientIp` uses the entry appended by the trusted proxy (`TRUSTED_PROXY_HOPS`).                     |
| 4   | Medium   | Payment-signature failure returned HTTP 502 (looked like an outage, could trigger client retries).                                                                                              | Returns 400 `VALIDATION_ERROR`; event stored with `signatureValid=false`.                           |
| 5   | Low      | Duplicate-payment refunds could have been counted against the order's refundable total.                                                                                                         | Separate accounting path for duplicate captures.                                                    |
| 6   | Low      | Contact-form submissions were stored but not visible to staff (risk of ignored customer issues).                                                                                                | Shown in Admin → Messages & emails.                                                                 |

## 4. Remaining risks and recommendations

1. **CSP allows `'unsafe-inline'` scripts.** Required by Next.js inline bootstrap without nonces. Mitigated by
   React escaping, no user HTML, strict `object-src`/`base-uri`/`frame-ancestors`. _Recommendation:_ adopt
   nonce-based CSP via `proxy.ts` before launch.
2. **Email verification is not required** (no email provider in local dev). Accounts can be created for
   addresses the user does not own. _Recommendation:_ enable `requireEmailVerification` once a provider is set up.
3. **No MFA for administrators.** _Recommendation:_ enable Better Auth's two-factor plugin for admin accounts.
4. **Rate limiting depends on correct proxy configuration.** Set `TRUSTED_PROXY_HOPS` to the real number of
   proxies; otherwise per-IP limits can be bypassed or applied too broadly.
5. **Sign-up reveals whether an email is registered** ("account already exists"). Common UX trade-off;
   mitigated by sign-up rate limiting.
6. **Real Razorpay round-trip not executed in this sandbox** (Razorpay hosts blocked). The code path is unit/
   integration tested with signed payloads and a mock gateway; run the README's test-mode checklist locally
   and register the webhook (with secret) in the Razorpay dashboard.
7. **Local disk storage** for uploads is not suitable for multi-instance hosting; move to object storage with
   the provided `StorageProvider` interface.
8. **Database least privilege.** Development uses one DB role that owns the schema. _Recommendation:_ in
   production use a migration role (DDL) and a separate runtime role limited to DML.
9. **Backups, monitoring, alerting, WAF/DDoS protection and secret rotation** are infrastructure tasks outside
   this phase.
10. **Legal/tax content** (policies, GST configuration, invoice format) are templates and must be reviewed by
    qualified professionals.
11. **Guest order access tokens do not expire** (they are HMACs of the order id). Rotating `BETTER_AUTH_SECRET`
    invalidates all tokens and sessions.
